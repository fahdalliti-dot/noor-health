# 05 - UI

Status: draft. Part of the design doc set in `docs/design/`.
Depends on: `01-architecture.md` (stack, i18n), `02-data-model.md` (entities), `03-auth-and-sessions.md` (login and 2FA flows), `04-api.md` (permissions, errors).

## 1. Principles

1. **Speed over decoration.** A secretary books dozens of appointments a day and a doctor sees a patient every 10 to 20 minutes. Every common task must take few clicks and be keyboard-friendly.
2. **Today first.** The home screen is the day's agenda, not a dashboard of charts.
3. **Show only what the role may use.** Hidden controls are a convenience. The server enforces permissions (see `04`).
4. **Safe by default.** Patient data is never shown where it is not needed, and destructive actions are always confirmed.
5. **Works on weak connections.** Light pages, fast first paint, clear behavior when the network drops.
6. **French and Arabic are equal citizens.** RTL is designed in from the first screen, not retrofitted.
7. **Accessible.** Readable by staff of all ages, with usable contrast, large touch targets and full keyboard operation.

## 2. Users and devices

| Role | Typical device | Main jobs |
|---|---|---|
| Secretary | desktop or laptop at the front desk | book and move appointments, register patients, take payments, print receipts |
| Doctor | desktop in the consulting room, sometimes a tablet | see the day's patients, read history, write notes and prescriptions |
| Admin | any | invite staff, clinic settings, audit log |

Supported viewports: 375px (phone, read and light use) through 1280px+ (primary). Tablets (768 to 1024px) must be fully usable. The doctor consultation screen and the agenda are designed for tablets first.

Browsers: current Chrome, Edge, Safari and Firefox. No support for legacy browsers.

## 3. Navigation

App shell: a collapsible side navigation, a top bar with global patient search, the user menu and the language switcher. On narrow screens the navigation collapses to a bottom bar or menu button.

| Item | secretary | doctor | admin |
|---|---|---|---|
| Agenda (home) | yes | yes | no |
| Patients | yes | yes | no |
| Billing | yes | yes | no |
| Consultations (my day) | no | yes | no |
| Team and invites | no | no | yes |
| Clinic settings | no | no | yes |
| Audit log | no | no | yes |
| Account (password, 2FA, sessions) | yes | yes | yes |

Global search (`/` or `Ctrl+K`): opens a patient search by name, phone or file number, from anywhere. Results show only identity fields (name, birth date, phone, file number).

## 4. Key screens

### 4.1 Agenda (home)
- Day view by default, with a week view. One column per doctor (secretary) or a single column (doctor).
- Appointment blocks colored by status (scheduled, confirmed, arrived, in progress, completed, cancelled, no-show). Never rely on color alone: each status also has a label or icon.
- Click an empty slot to create an appointment. Drag to reschedule, with a confirmation and a conflict message if the slot is taken (409 `slot_unavailable`).
- "Arrived" is one click for the secretary and moves the patient into the doctor's waiting list.
- Waiting list panel shows who is waiting and for how long.

### 4.2 Patient list and search
- Table with search, sorted by last visit or name. Server-side search and cursor pagination (see `04`).
- "New patient" opens a short form with only essential fields first (name, birth date, phone, insurance type). Extra fields can be added later.
- Possible-duplicate warning on creation with a link to the existing file.

### 4.3 Patient file
Header: name, age, file number, phone, insurance, next appointment, primary actions (new appointment, new consultation, new invoice).

Tabs, shown only if the role allows:
| Tab | Who sees it |
|---|---|
| Summary | all with `patients:read` |
| Appointments | all with `appointments:read` |
| Billing | all with `billing:read` |
| Documents (identity documents) | secretary and doctor |
| Consultations and history | doctor (or secretary with granted clinical access) |
| Medical profile (allergies, conditions, medications) | doctor (or granted) |
| Clinical documents (lab, imaging) | doctor (or granted) |

Allergies are shown as a prominent warning banner for doctors on every consultation screen. Secretaries without clinical access never see the tab and never receive the data.

### 4.4 Consultation screen (doctor)
- Opened from the agenda or the waiting list. Layout: patient context on one side (key history, allergies, last consultations), note editor on the other.
- Fields: reason, notes, diagnosis, vitals, prescription items, attachments.
- Draft saved automatically every few seconds. A visible "saved" indicator. Restores the draft after a refresh or a dropped connection.
- Specialty templates for notes (a simple list of reusable snippets) are a later feature, not in v1.
- "Sign" locks the consultation. After signing, changes are made through an amendment (see `02` and `04`).
- Prescription: add items quickly (name, dosage, frequency, duration), reorder, preview the PDF on clinic letterhead, then print or download.

### 4.5 Billing
- Create invoice from a consultation or a patient, add lines, issue, record payment (cash, card, transfer, cheque, insurance).
- Printable receipt (PDF) in the clinic's locale.
- **Daily cash summary:** totals by payment method for a chosen day, for closing the till.
- Voiding requires a reason and a confirmation.

### 4.6 Admin screens
- **Team:** list of staff, invite by email (role chosen), deactivate. Deactivation confirmation names the user and explains that their sessions end immediately.
- **Clinic settings:** name, address, logo (letterhead), locale, timezone, "require 2FA for everyone".
- **Audit log:** filter by user, action, date. Per-patient "who accessed this file" view.

### 4.7 Account and security
- Change password, set up or reset 2FA (QR code, recovery codes shown once with a prompt to save them), list and revoke own sessions with device labels.

## 5. Authentication UX

- **Login:** email and password, then the 2FA code step when required. Clear, non-revealing error messages (the same message for unknown email and wrong password).
- **2FA setup:** forced right after the first login for doctors and admins. The user cannot reach the app until it is completed.
- **Invite acceptance:** a page opened from the email link where the new user sets a password and completes 2FA setup if their role requires it.
- **Session expiry:** when a session ends, keep the user's unsaved draft in the browser until they sign back in, then return them to the same page.
- **Idle auto-lock:** after a configurable idle period (default 15 minutes) the screen locks with patient data hidden and asks for re-authentication. This matters in shared consulting rooms and waiting areas.
- **Privacy:** no patient names in page titles, browser history entries beyond opaque IDs, or analytics (see `01`).

## 6. Internationalization and RTL

- Languages: French (default) and Arabic. English is optional for staff, not a priority.
- Direction derives from the locale: `dir="rtl"` for Arabic. Use CSS logical properties (`margin-inline-start`, `padding-inline-end`, `text-align: start`) everywhere, never left/right.
- Mirror layout-direction elements (navigation, back arrows, breadcrumbs, progress). Do not mirror numbers, media controls or phone numbers.
- Digits: Western digits (0 to 9) in both languages, as customary in Morocco. Dates use the Gregorian calendar. The first day of the week is a clinic setting (default to confirm with pilot clinics).
- Mixed content: patient names, phone numbers and medication names may mix scripts. Wrap user-entered text in `dir="auto"` so it renders correctly inside either direction.
- Formatting: dates, times and money use `Intl` with the clinic timezone and `MAD`. Never build date strings by hand.
- All strings live in message catalogs (`next-intl`). No hardcoded text. Strings are written to survive 30% length growth (French is longer than English).
- Fonts: choose a family with good Arabic and Latin support, load only the weights used, with a fallback stack.
- Server-generated PDFs (prescriptions, receipts) and reminder messages use the clinic or user locale and must also be checked in RTL.
- Every new screen is reviewed in both languages before it is considered done.

## 7. Design system and components

- **Stack:** Next.js, TypeScript, Tailwind. A small set of accessible primitives (for example Radix UI or shadcn/ui) for dialogs, menus, tabs, comboboxes and date pickers. Do not build these from scratch.
- **Tokens:** one place for colors, spacing, type scale, radii and shadows. Support light mode first. Dark mode is optional later.
- **Look and feel:** calm, clinical and trustworthy. High contrast text, restrained color, color reserved for status and primary actions. No decorative animation.
- **Core components:** App shell, Agenda grid, Appointment card, Data table, Patient search combobox, Form field, Status badge, Confirm dialog, Toast, Empty state, Skeleton, PDF preview.
- **Forms:** visible labels on every input (placeholders only for format hints). Validate on blur and clear errors as soon as they are fixed. Submit buttons stay clickable and report problems instead of staying disabled. Use shared Zod schemas from `packages/shared` for validation so client and server agree.
- **Buttons:** verb-first labels ("Create patient", "Record payment"). Never "OK" or "Submit".
- **Destructive actions:** the confirmation dialog names the thing being affected and the consequence.

## 8. States

Every screen and list defines all of these:

| State | Behavior |
|---|---|
| Loading | skeletons for content longer than about a second, nothing for fast loads (avoid flicker) |
| Empty | explains what belongs here and offers the next action ("No appointments today. Create one.") |
| No results | says what was searched and how to adjust it, without echoing patient data into the URL |
| Error | plain language, a retry option, and the request ID so staff can report it |
| Forbidden | explains that the role does not have access, without exposing whether the record exists |
| Offline or slow | banner explaining the connection problem, queued drafts kept locally |

## 9. Performance and weak connectivity

- Target first useful screen quickly on a mid-range laptop and a modest connection. Budgets: small JavaScript per route, code splitting by route, images optimized.
- Prefer server rendering for list and detail screens. Cache read-only reference data (clinic settings, staff list) on the client.
- Consultation drafts are autosaved. If the connection drops, keep edits locally and sync when back online with a clear status. Full offline mode is out of scope for v1.
- Do not poll aggressively. Refresh the agenda on focus and at a modest interval.
- Avoid large client libraries. Check bundle size in CI.

## 10. Accessibility

Target: WCAG 2.2 AA.
- Full keyboard operation with visible focus rings. Focus is trapped inside dialogs and restored on close.
- Sufficient contrast, status never conveyed by color alone, text resizable to 200%.
- Touch targets at least 44px on tablets.
- Semantic HTML, labeled controls, correct landmarks, announcements for toasts and autosave status.
- Respect `prefers-reduced-motion`.
- Tested with a screen reader in both languages for the main flows before launch.

## 11. Keyboard shortcuts (secretary and doctor speed)

| Shortcut | Action |
|---|---|
| `/` or `Ctrl+K` | patient search |
| `N` then `P` | new patient |
| `N` then `A` | new appointment |
| `Ctrl+S` | save draft (consultation) |
| `Esc` | close dialog or panel |

Shortcuts are listed in a help dialog and never fire while typing in a field.

## 12. Printing and documents

- Prescription and receipt PDFs use the clinic letterhead (logo, name, address, phone), the doctor's name and license number, and the clinic locale.
- Print styles for the agenda day sheet are optional in v1.
- Documents must render correctly in Arabic RTL and in French, including mixed-script names.

## 13. Testing

- Component tests for the shared primitives.
- Playwright end-to-end tests for the critical flows: invite and first login with 2FA, create patient, book and move an appointment, run a consultation and sign it, issue an invoice and record a payment, secretary blocked from clinical data, clinic A cannot see clinic B.
- Run the critical flows in both French and Arabic (RTL).
- Automated accessibility checks (axe) in CI on key screens.
- Fake data only, in every test and screenshot.
